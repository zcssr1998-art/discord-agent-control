# DSH 智能团队 Manager / Worker 架构对照实验

> 任务类型：受控实验 + 最小必要的 DSH 模式配置  
> 优先级：中  
> 目标：用有限的模型额度，验证“高智力 Manager 决策 + DeepSeek Worker 执行”是否比单模型全流程更有效，以及 Manager 自身消耗占比究竟有多大。

## 0. 先明确实验目的

本实验不是为了堆 Agent 数量，也不是为了展示团队协作过程，而是回答三个实际问题：

1. **DS 全流程单 Agent** 与 **DS 只做 Manager、DS 子代理负责生产** 相比，完成质量、总成本和耗时有什么差异？
2. Manager 只负责理解、规划、分工、监控、疑难处置和 Review 时，其自身 DS 消耗是否低于单 Agent 全流程消耗的 10%？
3. 把 Manager 换成 **GPT Sol 6.1 高思考（Codex 订阅额度）**，Worker 仍全部使用 **Cline DeepSeek**，是否能明显提高任务完成率、质量或速度？提高幅度是否值得消耗 Codex 额度？

特别注意：

- **Manager 自身消耗低，不等于整个团队总成本低。** 必须同时统计 Manager、全部 Workers 和全系统总消耗。
- GPT Sol 6.1 的结果只能验证“高智力模型担任 Manager”的架构价值，不能直接等同于 Opus 5.5 的效果。若结果明显有价值，后续再用同一套任务做一次 Opus 小样本验证。
- 本实验是筛选性基准，不是大样本统计研究。结果接近时不要过度下结论。

## 1. 执行前：检查 DSH 现有实现

先在当前实际 DSH 项目工作区执行，不要把本任务书所在的仓库误认为 DSH 源码仓库。

按最低必要范围检查：

1. 读取当前 DSH 项目的 AGENTS.md（若存在）及其指向的中央规则。
2. 检查当前任务状态、Git branch / HEAD / status / diff，以及已有智能团队、Manager、Worker、模型路由和用量统计实现。
3. 优先复用现有智能团队和模型路由能力，不要重建 Agent 框架。
4. 确认当前 Cline DeepSeek 路由和已导入的 Codex 额度可用。
5. 确认 DSH 是否能分别指定 Manager 模型和 Worker 模型，并能在运行时验证父子 Agent 的实际模型身份。

### 1.1 实验模式配置要求

本次需要三种可选实验配置：

| 配置 ID | Manager | Worker | 角色限制 |
|---|---|---|---|
| DS-SOLO | Cline DeepSeek | 无子代理 | 主 Agent 独立完成全流程 |
| DS-MANAGER | Cline DeepSeek | Cline DeepSeek | Manager 只管理，Worker 负责生产 |
| GPTSOL-MANAGER | GPT Sol 6.1 高思考（Codex） | Cline DeepSeek | Manager 只管理，Worker 负责生产 |

要求：

- 如果现有 DSH 已支持混合模型团队，只配置实验预设，不改造底层。
- 如果只缺少 Manager / Worker 模型分离能力，基于现有团队机制做**最小、可回滚的接线改动**，不要新建第二套编排引擎。
- 新配置必须可明确选择，且不能改变原有默认模式、普通聊天模式或其他模型路由。
- GPTSOL-MANAGER 中，只有 Manager 使用 GPT Sol 6.1 高思考；所有子代理必须使用 Cline DeepSeek。
- 不允许模型静默回退。实际模型与预期不一致，该次运行标记 INVALID，不纳入对照。
- 如果现有能力无法安全实现混合模型路由，先报告具体阻塞和最小替代方案，不要用多个互不关联的聊天窗口冒充智能团队。

完成配置后先做一次极小的身份验证：确认 Manager 和 Worker 的真实模型、角色、父子关系及用量记录。该验证不计入正式任务成绩，但记录其成本。

## 2. 三组实验定义

### A 组：DS-SOLO 基准组

- 主 Agent：Cline DeepSeek。
- 不允许创建子代理。
- 同一个 Agent 负责需求理解、规划、实现、测试、Debug、Review 和交付。
- 允许正常使用工具。
- 这是“DS 全程参与任务”的基准。

### B 组：DS-MANAGER 分工组

- Manager：Cline DeepSeek。
- Worker：全部为 Cline DeepSeek 子代理。
- Manager 负责理解需求、拆解任务、分配工作、跟踪进度、处理疑难、协调冲突、Review 和决定是否验收。
- **Manager 不得直接生产或修改任务交付物**，包括代码、测试文件、数据分析脚本和最终报告文件。
- Manager 可以读取文件、查看 Diff、读取精简日志、运行或要求运行测试、分析错误，并把修复方案分配给 Worker。
- 所有实际生产和文件修改由 Worker 完成。

### C 组：GPTSOL-MANAGER 高智力主控组

- Manager：GPT Sol 6.1 高思考，使用已导入的 Codex 订阅额度。
- Worker：全部为 Cline DeepSeek 子代理。
- Manager 的权限边界、任务范围和验收标准与 B 组完全相同。
- Manager 不得亲自写代码、修改交付文件或代替 Worker 完成生产。
- GPT 只负责决策、分工、疑难处置、协调和 Review。
- 不得把 Worker 偷换成 GPT，也不得在 GPT 额度不足时静默回退到其他模型。

### 2.1 团队规模限制

- B、C 两组默认每个任务使用 2 个 DS Worker。
- 确有独立工作可并行时最多 3 个 Worker；不允许为了展示团队规模而空开 Agent。
- 同一任务最多 2 个 Worker 同时执行，避免资源和上下文失控。
- Worker 任务应尽量独立，避免多个 Worker 同时改同一文件。
- Manager 不重复理解、重复规划同一任务；优先派发明确任务并等待结果。
- 不把完整长日志反复发给 Manager，只传失败命令、Exit Code、核心错误和必要上下文。

## 3. 正式测试任务

总计 **3 种任务 × 3 组 = 9 次正式运行**。每次运行使用独立、干净的临时工作区。

所有组必须使用完全相同的任务描述、输入文件、运行环境和验收标准。任务模板只准备一次，生成后冻结；正式运行不得临时修改输入。

### T1：代码 Debug 与边界处理

**目标：** 验证 Agent 能否识别已有实现中的多个逻辑问题，修复并补齐测试。

在独立工作区创建 package.json（使用 Node.js 20、ESM、无第三方依赖）和 src/price.mjs，初始代码如下：

~~~js
export function calculateFinalPrice({
  unitPrice,
  quantity = 1,
  memberTier = "regular",
  coupon = null
}) {
  let total = unitPrice * quantity;

  if (memberTier === "gold") {
    total *= 0.9;
  }

  if (coupon?.type === "percent") {
    total *= 1 - coupon.value;
  }

  if (coupon?.type === "fixed") {
    total -= coupon.value * quantity;
  }

  return Math.max(0, Number(total.toFixed(2)));
}
~~~

**任务要求：**

修复函数，并补充自动化测试。正确业务规则如下：

1. 商品小计 = unitPrice × quantity。
2. unitPrice 必须是有限且不小于 0 的数字。
3. quantity 必须是正安全整数。
4. memberTier 只允许 regular 或 gold；gold 会员先享受 10% 折扣。
5. percent 优惠券的 value 表示百分比数值，例如 15 表示 15%，合法范围 0–100；在会员折扣后计算。
6. fixed 优惠券的 value 表示固定金额，合法范围不小于 0；在会员折扣后只减一次，不乘 quantity。
7. coupon 为 null 表示没有优惠券；未知类型或非法优惠券数据应明确报错。
8. 最终金额不能小于 0，最终结果保留两位小数。
9. 不得修改调用方传入的对象。

至少覆盖：

- 普通用户、无优惠券；
- Gold 会员折扣；
- 百分比优惠券；
- 固定金额优惠券；
- 会员折扣与优惠券叠加；
- 固定优惠券超过应付金额；
- 0 元商品；
- 非法价格、数量、会员等级和优惠券；
- 金额精度边界。

**交付物：**

- 修复后的函数；
- 自动化测试；
- 简短根因说明；
- 测试命令和真实运行结果。

### T2：从零实现一个小型任务 CLI

**目标：** 测试需求拆解、模块设计、并行实现、集成和真实验收能力。

在独立空白工作区，使用 Node.js 20 和标准库，实现一个可持久化的任务管理 CLI，不使用第三方依赖。

**命令接口：**

- add：新增任务，接收 title。
- list：列出全部任务。
- list --status open：只列出未完成任务。
- list --status done：只列出已完成任务。
- done <id>：将指定任务标记为完成。
- delete <id>：删除指定任务。
- --db <path>：可选数据库路径；未提供时使用当前目录下的 tasks.json。

**数据规则：**

- 每个任务包含 id、title、status、createdAt、updatedAt。
- id 为从 1 开始递增的正整数，不得与已有任务重复。
- title 必须 trim，长度为 1–120 个字符。
- status 只能是 open 或 done。
- 时间字段必须为合法 ISO 8601 时间。
- 命令执行后必须持久化，重新启动进程后数据仍然存在。
- 文件写入采用同目录临时文件 + rename 的原子替换方式。
- 数据文件损坏或 JSON/schema 非法时，必须报错退出，不能静默覆盖原文件。
- 不存在的任务 ID、非法参数、空标题必须返回明确错误和非零退出码。
- 输出结构应稳定、便于脚本解析；错误信息写入 stderr。

**验收：**

1. 新增两条任务，ID 正确递增。
2. list 能读取完整数据。
3. open / done 筛选正确。
4. done 后状态和更新时间正确。
5. delete 后任务确实消失。
6. 退出进程后重新运行，数据仍然存在。
7. 空标题、非法 ID、未知命令能正确拒绝。
8. 损坏的 JSON 不会被覆盖或清空。
9. 原子写入逻辑和异常路径有测试。
10. 提供 npm test 或等价的确定性测试命令，必须真实运行通过。

**交付物：**

- 完整 CLI；
- 自动化测试；
- README 使用说明；
- 测试命令及真实运行结果。

## 4. 实验控制变量

每个任务、每组都必须遵守：

- 使用独立工作目录，禁止共享前一组的代码、结果、日志或上下文。
- 同一任务的初始文件和输入数据完全相同；正式运行前冻结模板并记录 SHA256。
- Node.js 统一使用 Node 20；其他依赖和环境保持一致。
- 工具权限、网络权限、超时和验收标准一致。
- 不允许额外调用其他高价模型辅助某一组。
- 不允许把前一组的解法、代码或错误分析传给后一组。
- 任务执行顺序按任务轮换，降低服务负载和时间顺序影响：
  - T1：A → B → C
  - T2：B → C → A
  - T3：C → A → B
- 每次正式运行硬超时 25 分钟。超时即记录，不得无上限延长。
- 只有明确的环境/基础设施故障允许重试一次；模型推理失败、实现失败和返工属于真实实验结果，不得当作环境故障删除。
- 不为追求 PASS 隐瞒失败、删减测试或降低验收标准。

## 5. Codex 五小时额度保护

C 组必须严格控制 GPT Sol 6.1 高思考的调用量：

1. 运行前记录 Codex 当前 5 小时额度剩余情况。
2. GPT 只用于 Manager 的必要决策，不用于写代码、写测试、生成报告或独立评估。
3. 每个任务 Manager 最多 3 次实质性决策调用：初始规划/派发、必要的疑难处置、最终 Review。没有必要时不得凑次数。
4. 不把完整日志和大段文件反复输入 GPT；只传关键 Diff、失败测试、Exit Code 和必要上下文。
5. C 组总消耗达到启动时可用 5 小时额度的 25% 时，立即停止后续 C 组任务，记录部分结果并报告，不得自动继续消耗。
6. 如果无法读取可靠的额度剩余值，先只执行 C-T1，记录实际消耗并暂停，不得盲目跑完剩余任务。
7. 不允许为了补齐实验数据突破额度上限。

## 6. 必须采集的指标

每次运行建立独立记录，至少包含：

### 6.1 模型和角色

- 运行 ID：T1-A、T1-B、T1-C 等。
- Manager 实际 Provider / Model / Thinking Level。
- 每个 Worker 的实际 Provider / Model。
- Manager 与 Worker 的父子会话关系。
- Worker 数量、最大并发数。
- 是否发生模型回退或角色错配。

### 6.2 消耗

分别统计 Manager 和每个 Worker：

- Input tokens；
- Cached input tokens；
- Output tokens；
- Reasoning tokens（若可获得）；
- Total tokens；
- 请求次数；
- API 实际费用或可核实的计费金额；
- 订阅额度消耗。

必须区分：

- **DS Manager 消耗**
- **DS Workers 消耗总和**
- **DS 全部消耗 = DS Manager + DS Workers**
- **GPT Manager 消耗**
- **全系统综合消耗 = 全部 DS + GPT Manager**

如果平台显示的团队总用量已经包含子代理，不能再把子代理用量重复相加。

### 6.3 效率和质量

- 从任务开始到完成的实际耗时。
- 是否在 25 分钟内完成。
- 自动化测试 / 验收通过情况。
- 返工次数。
- Manager 额外干预次数。
- Worker 数量及并行情况。
- 最终交付物是否完整。
- 是否出现重复劳动、错误分工、遗漏需求或无效 Agent。
- 如能进行盲评，按统一 100 分标准评价：正确性 50、完整性 20、健壮性 15、可维护性 10、结果表达 5。没有独立评估证据时不得虚构评分。

若某个 Provider 无法提供精确 Token 或费用数据，明确标记 N/A，不得用模型估算值冒充真实消耗。

对于 Codex 订阅，不得把额度百分比擅自换算成美元。单独记录 5 小时额度使用前后变化；只有存在可核实的官方等价计费口径时才可换算。

## 7. 核心对比公式

### 7.1 DS Manager 自身消耗占比

DS-MANAGER 组：

DS Manager 占比 = DS Manager tokens ÷（DS Manager tokens + DS Workers tokens）

并单独计算：

DS Manager 相对基准消耗 = DS Manager tokens ÷ DS-SOLO 对应任务 tokens

这两个指标可以回答“Manager 本身是否只消耗了基准 DS 的 10%”。

### 7.2 整个团队是否真的省钱

DS 分工组总成本 = DS Manager 成本 + 全部 DS Worker 成本。

分工组相对基准成本变化：

1 -（DS-MANAGER 总成本 ÷ DS-SOLO 总成本）

结果为正表示节省；结果为负表示更贵。

**不能拿 DS Manager 自身的 10% 消耗，冒充整个团队只花了 10%。** 必须把 Worker 成本全部算进去。

### 7.3 高智力 Manager 是否值得

比较 B 与 C：

- 完成率和验收通过率；
- 质量评分（有独立证据时）；
- 完成耗时；
- DS Worker 消耗变化；
- Manager 决策调用次数；
- GPT 五小时额度消耗；
- 全系统综合成本。

订阅额度与按量 API 成本分开呈现，不做未经证实的统一换算。

## 8. 验收与结论标准

最终必须回答：

1. DS Manager 自身消耗占 DS-SOLO 基准的多少？
2. DS Manager 占整个 DS 团队消耗的多少？
3. 加入 DS Workers 后，B 组整个团队到底比 A 组便宜还是更贵？
4. B 组是否更快？是否减少或增加返工？
5. C 组相对 B 组是否提高了任务完成率、质量或速度？
6. GPT Sol 6.1 的额度消耗是否值得这些提升？
7. 现有证据是否足以支持购买 Opus 5.5，还是应先做 Opus 单任务试点？

参考判断：

- 如果 B 与 A 的完成质量接近，且 B 总成本更低或单位成功任务成本更低，说明 DS 管理/分工架构有价值。
- 如果 DS Manager 自身消耗低于基准的 10%，但 DS Workers 让团队总成本显著上升，不能判定整体省钱。
- 如果 C 相比 B 的质量、完成率和速度没有实质改善，就没有足够证据为高智力 Manager 支付额外额度。
- 如果 C 明显胜出，也只能证明高智力 Manager 值得进一步验证；不能直接宣称 Opus 5.5 必然更好。
- 只有当完成质量、成本和耗时的改善同时有数据支撑时，才提出架构推荐。

## 9. 安全、范围和停止条件

- 本实验的代码、CSV 和报告全部在独立临时工作区中产生。
- 不修改 Jarvis 生产代码、配置、凭证或线上服务。

- 不把实验工作区的临时产物误提交到 DSH 或 Jarvis 源码仓库。
- DSH 模式配置如有代码改动，只能改当前实际 DSH 项目，先检查现有实现并做最小可回滚改动。
